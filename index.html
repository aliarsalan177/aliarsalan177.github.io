03 / Leadership

How I lead

Six things I'm accountable for on a team, each with the work that backs it up rather than the adjective on its own.

01

Technical direction

Choosing the architecture a team will live with for years, and being the one accountable when that choice is tested.

Picked Single-SPA for Salla 4.0 so squads could deploy dashboard modules independently, then held the seams as the estate grew.

02

Architecture at scale

Systems that stay comprehensible as they grow — clear boundaries, shared contracts, and no module that only one person can touch.

Designed the micro-frontend ecosystem spanning React, Vue and Next.js, with a shared UI SDK every engineering squad builds against.

03

Engineering standards

Turning “we should probably” into something the CI actually enforces, so quality survives the next deadline.

Set the auth, state, testing and CI/CD standards for the platform, and held Lighthouse 90+ as a budget rather than an aspiration.

04

Leading migrations

The work nobody volunteers for: moving a live product onto new foundations without its users noticing.

Led the engineering migration of Salla Ads after the Sweply acquisition — users, data and advertising workflows onto the new architecture.

05

Growing engineers

Review as teaching rather than gatekeeping, and documentation written on the assumption that the next person is not me.

Mentored engineers across squads and published 36 engineering guides distilling the fundamentals into rules and interview questions.

06

End-to-end ownership

Backend, frontend, mobile and the deploy. Owning the whole path is what makes an architectural opinion worth listening to.

Shipped GymOS solo — multi-tenant Postgres backend, Next.js desk, biometric hardware integration, Docker image and Windows installer.

04 / Selected Work

Things I've built

Each one as the problem it solves, what I actually built, and what changed because it exists — designed, shipped and maintained end to end.

Featured2026

throttle.ai

Problem · AI coding agents resend the same context on every turn, so a long session burns tokens re-reading files nothing has touched.

Built · A transparent local proxy that speaks each provider's exact wire protocol, so neither side knows it is there. Prompt caching, context deduplication and diff-based file compression, bound to 127.0.0.1 so nothing leaves the machine.

Impact · 50–90% fewer tokens per session with no loss of context, and it drops in without changing the agent: Claude Code, Cline, Continue and aider all speak to it unmodified. 158 tests, ~99% coverage.

  • TypeScript
  • LLM proxy
  • Token optimization
  • Prompt caching
  • Node ≥20
  • AI infra
Featured2026

Formwright

Problem · Every product I worked on rebuilt the same forms, tables and dialogs, and every rebuild carried its own bugs.

Built · Three engines sharing one signal graph: forms, tables and overlays, each defined as a schema and rendered to surgically-updating DOM. No virtual DOM, no full re-renders, and a schema plain enough for an LLM to write.

Impact · 11 packages on npm, ~62 KB gzipped for the whole suite, zero runtime dependencies. Running in production in GymOS, where every form, table and dialog is rendered by it.

  • TypeScript
  • Signals
  • Zero-deps
  • npm packages
  • LLM schema
  • Web Components
Featured2026

GymOS — Gym Management System

Problem · Gyms in the region run on paper and WhatsApp, and the software that exists assumes reliable internet and one location.

Built · Multi-tenant Postgres with a tenant-scoped Prisma layer, biometric door hardware over ZKLib, offline-first attendance, invoicing with thermal receipts, role-based admin and 2FA.

Impact · A live multi-tenant product at gymos.shop, shipped three ways from one codebase — web app, Docker image and Windows installer — and the proving ground that keeps the Formwright engines honest.

Built · A field-mapping layer between any store's API and one internal schema, driving orders, products, customers and carrier shipping from a single model.

Impact · Integrations became configuration: map an external API's fields to the internal schema in the UI and orders sync without a release.

05 / Open Source

Published on npm

11 packages under the @formwright scope — three engines that share one signal graph, zero runtime dependencies between them and the outside world. Installed and running in production in the gym platform below.

5 packages

Form engine

Define a form as data, render it to surgical DOM.

A schema describes the fields, validation and layout; the engine renders and updates only the nodes that changed. No virtual DOM, no full re-renders, and the schema is plain enough for an LLM to write.

  • @formwright/schema
  • @formwright/core
  • @formwright/dom
  • @formwright/reactive
  • @formwright/ai
3 packages

Grid engine

Tables, sorting, filtering and row actions from the same schema.

The data-grid half of the suite: columns, sorting, filters, pagination and row actions declared as data, sharing the signal graph with the form engine so a filter and a form field can drive each other.

  • @formwright/grid-schema
  • @formwright/grid-core
  • @formwright/grid-dom
3 packages

Overlay engine

Modals, drawers, sheets, popovers and toasts — callable from anywhere.

The hard parts of a dialog, done once: the stack, the focus trap, the iOS scroll lock, drag-to-dismiss, escape and backdrop handling. One host component mounts it, and any code in the app can open an overlay without a provider in scope.

  • @formwright/overlay-schema
  • @formwright/overlay-core
  • @formwright/overlay-dom
